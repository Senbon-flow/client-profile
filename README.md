# Мини-профиль клиента по транзакциям

Сервис считает по клиенту доходы и расходы по месяцам, топ-3 категории трат и число
уникальных контрагентов по операциям за январь–июнь 2026. Все суммы в KGS.

## Как запустить

Нужен Python 3.10+. Положите `transactions.csv` и `mcc_categories.json` в папку `data/`
(в репозитории её нет, данные не хранятся в git). Затем:

```
pip install -r requirements.txt
uvicorn src.app:app
```

Пример запроса:

```
http://127.0.0.1:8000/clients/1010/profile?date_from=2026-01-01&date_to=2026-06-30
```

Коды ответов: `200` профиль, `400` неверный формат или несуществующая дата (а также
`date_from` позже `date_to`), `404` клиента нет в данных.

Другие команды:

```
python -m src.loader          # только загрузка и валидация, пишет rejected.csv
python -m src.sql_profile 1010  # то же по месяцам через SQL, сверка с Python
pytest                        # тесты
```

## Структура

- `src/loader.py`: загрузка CSV, валидация, `rejected.csv`
- `src/profile.py`: `build_profile(client_id, date_from, date_to)`
- `profile.sql`: тот же расчёт по месяцам одним запросом с CTE (SQLite)
- `src/sql_profile.py`: загрузка чистых данных в SQLite и запуск `profile.sql`
- `src/app.py`: HTTP-сервис (FastAPI)
- `tests/`: тесты pytest

## Какие проблемы нашли в данных

Из 2056 строк принято 2013, отброшено 43 (они сохраняются в `rejected.csv` с колонкой `reason`).

| Проблема | Строк | Что сделали |
|---|---|---|
| Полностью одинаковые дубли `tx_id` | 20 | оставили первую, остальные в `rejected.csv` (`duplicate_tx_id`) |
| Один `tx_id`, но разные суммы (отличаются ровно в 10 раз) | 6 (3 id) | отбросили обе копии (`conflicting_duplicate`): неизвестно, какая верная |
| Сумма пустая или `n/a` | 6 | отбросили (`invalid_amount`) |
| Сумма 0 или отрицательная | 7 | отбросили (`non_positive_amount`) |
| Дата пустая, `yesterday`, несуществующая (`2026-13-40`, `2026-02-30`) | 4 | отбросили (`invalid_datetime`) |
| Сумма вида `2 984,26` (пробел, запятая) | 12 | привели к числу |
| Дата `дд.мм.гггг чч:мм` вместо ISO | 25 | распарсили |
| Пробелы вокруг id (`' 1003 '`) | 5 | обрезали пробелы |
| MCC с ведущим нулём (`05812`) | 7 | привели к `5812` |
| MCC, которого нет в словаре (`1234`) | много | категория `other` |
| Валюта USD | 10 | пересчитали в KGS по курсу-константе (см. допущения) |
| Переводы самому себе | 15 | остаются в данных, но в профиль не входят |

## Допущения

- **Курс USD.** В данных курса нет, поэтому в `src/loader.py` стоит константа `USD_TO_KGS = 87.5`.
  Это допущение, а не реальный курс. Поменять можно в одном месте.
- **Отрицательные суммы** считаем ошибкой данных и отбрасываем. Неясно, это возврат или ошибка,
  а знак «входящая/исходящая» уже задаётся плательщиком и получателем.
- **Клиент** это id вида `10xx`. Торговцы и работодатели клиентами не считаются, для них ответ `404`.
- **Контрагент** это тот, кому клиент платил и от кого получал.
- **Период** включает обе границы (`date_from` и `date_to`).

## Почему переводы самому себе не учитываются

Если `payer_id == payee_id`, деньги просто перешли между своими счетами: клиент не получил
дохода и ничего не потратил. Если их учесть, входящие и исходящие вырастут на одну и ту же
сумму (в данных такие переводы доходят до 499 000), и профиль покажет доходы и расходы,
которых не было. Кроме того, клиент стал бы «контрагентом» самому себе.

## Что изменю, если строк будет 50 миллионов

Сейчас весь CSV читается в память pandas, каждая строка проверяется циклом Python, а сервис
держит всю таблицу в памяти. На 2 тысячах строк это нормально, на 50 миллионах нет.

- **Отделить загрузку от сервиса.** Валидация и очистка идут отдельной задачей (батчами или
  потоком), результат пишется в базу, например PostgreSQL или ClickHouse. Сервис читает из базы,
  а не из CSV при старте.
- **Типы и ограничения в базе.** Сумма в `NUMERIC` (а не `float`), время в `timestamptz`,
  `tx_id` с `UNIQUE`: дубли отсекаются самой базой (`ON CONFLICT DO NOTHING`), а конфликтующие
  ловятся отдельным запросом. Отброшенные строки пишутся в таблицу `rejected` с причиной.
- **Индексы и партиции.** Индекс по `(payer_id, tx_datetime)` и `(payee_id, tx_datetime)`;
  партиционирование таблицы по месяцам, чтобы запрос за период читал только нужные партиции.
- **Предрасчёт.** Месячные суммы по клиентам хранить в агрегированной таблице (или
  материализованном представлении) и обновлять инкрементально. Запрос профиля тогда читает
  десятки строк, а не миллионы.
- **Курсы валют** хранить таблицей «валюта, дата, курс» и конвертировать по дате операции,
  а не одной константой.
- **Формат файлов.** Для исходных выгрузок использовать Parquet вместо CSV (сжатие, типы,
  чтение нужных колонок), а для аналитики можно взять DuckDB.
- **Кэш и мониторинг.** Кэшировать готовые профили, считать долю отброшенных строк по причинам
  и поднимать тревогу, если она резко выросла.
- **Тесты** оставить на маленьких наборах, а для базы добавить интеграционный тест на небольшой
  копии данных.
